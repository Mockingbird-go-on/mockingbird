# Вопросы и ответы по резюме (собеседование DevOps-инженер)

1. **Вы описываете гибридную DNS-систему на базе Bind9, PowerDNS и DNS AD с управлением через GitLab CI. Как вы организовали автоматическое тестирование зон перед деплоем и что делаете при ошибках?**

Я настроил GitLab CI пайплайн, который при каждом push в репозиторий с зонами выполняет следующие шаги:
- Валидация синтаксиса — для Bind использую named-checkzone, для PowerDNS — pdnsutil check-zone, для AD — проверяю через PowerShell команды Test-DnsZone.
- Семантическая проверка — скрипты на Python проверяют отсутствие дублирующих записей, корректность MX, SPF, DKIM, а также пересечения с уже существующими зонами (предварительно загружаю текущие зоны из git или через API).
- Тестирование разрешения — поднимаю изолированный контейнер с копией DNS-сервисов, загружаю новые зоны и прогоняю набор тестовых запросов (например, проверка A, CNAME, SRV для критичных сервисов).
- Если все тесты проходят, пайплайн создаёт merge request, после ревью и аппрува выполняется apply (обновление конфигураций через Ansible). При ошибке пайплайн падает, а роллбэк реализован через сохранение предыдущего состояния в git и автоматический откат (ansible-роль, которая восстанавливает бэкап зон). Также настроен алерт в Telegram о неудачном деплое.

2. **Как вы обеспечиваете высокую доступность гибридной архитектуры Windows + Linux в Naumen? Какие практики используете для отказоустойчивости?**

Мы строим HA на нескольких уровнях:
- На уровне приложений — используем кластеризацию (Patroni для PostgreSQL, Active Directory с несколькими DC, Exchange DAG).
- На уровне инфраструктуры — все критичные VM размещаются на кластерах VMware с vSphere HA и DRS, для части Linux-сервисов (например, балансировщики) — Keepalived + HAProxy.
- Резервирование сетевых сервисов — DNS у нас мультимастерная (Bind + PowerDNS + AD), почта — гибрид Exchange + Postfix с балансировкой.
- Мониторинг и автоматическое восстановление — настроены алерты и self-healing через Ansible (например, перезапуск сервиса при падении) и Kubernetes (replicasets, readiness probes).
- Регулярные восстановительные тесты — например, выключаем узлы в staging по сценариям отказоустойчивости и записываем runbooks для типовых сценариев.

3. **В резюме вы упомянули, что внедрили Terraform с удалённым хранением state в S3 и блокировками. Расскажите, как именно вы организовали работу с состоянием в команде и как интегрировали это с GitLab CI.**

Мы используем бэкенд S3 (в Cloud.ru/VK Cloud) с блокировками на уровне объекта (object lock/условные записи; в случае AWS S3 — это DynamoDB). State-файлы хранятся по принципу: bucket/environment/project/terraform.tfstate. Каждый проект имеет свой ключ.
- В GitLab CI пайплайн при создании MR выполняет terraform plan и выводит diff в комментарий к MR.
- После ревью и мержа в main ветку запускается terraform apply с автоматическим подтверждением (только для dev/stage), для prod — ручной триггер через web-интерфейс GitLab.
- Блокировки предотвращают конкурентное изменение — если кто-то уже запустил apply, другие пайплайны ожидают или падают с ошибкой.
- Мы также настроили versioning на S3 бакете, чтобы можно было восстановить предыдущий state в случае катастрофы.

4. **Вы написали, что время создания типовой инфраструктуры сократилось с 2 часов до 15 минут. Какие конкретно компоненты вы автоматизировали и какие были самые сложные моменты?**

До внедрения IaC инфраструктура (сети, VM, БД, Kubernetes) создавалась вручную через веб-консоль. Мы автоматизировали:
- Создание VPC, подсетей, маршрутов, security groups через Terraform.
- Развёртывание VM с нужным OS, установкой агентов мониторинга, SSH-ключей, базовых пакетов через Terraform + cloud-init + Ansible.
- Настройку кластеров БД (Patroni) и Redis через Terraform + Ansible роли.
- Деплой Kubernetes кластера (managed от Cloud.ru) и установку базовых add-онов (Ingress, cert-manager, monitoring stack) через Terraform + Helm.

Сложности:
- Интеграция с существующими ресурсами (некоторые были созданы вручную) — пришлось импортировать их в state, что было кропотливо.
- Управление зависимостями между модулями (сети должны быть созданы до VM).
- Работа с секретами — интегрировали Vault для динамических секретов и передачу их в Terraform через переменные окружения.
- Тестирование изменений — написали набор terratest для проверки корректности после apply.

5. **Расскажите, как вы настраивали сбор метрик с Windows-хостов через windows_exporter и VictoriaMetrics? С какими проблемами столкнулись?**

Мы установили windows_exporter на каждый Windows-сервер как службу (через Ansible win_package). Настроили сбор метрик CPU, RAM, дисков, сети, процессов, а также специфические метрики IIS и MS SQL через дополнительные collectors.
- VictoriaMetrics у нас развёрнута в кластере (vminsert, vmstorage, vmselect) для горизонтального масштабирования.
- Для Windows-хостов использовали vmagent в режиме pull (вытягивает метрики с windows_exporter), но для сегментов с NAT/фаерволом мы переключили на push-протокол: vmagent на каждом хосте отправляет метрики напрямую в vminsert (через --remoteWrite.url).

Проблемы:
- Высокое потребление памяти на windows_exporter при включении всех collectors — оптимизировали, включив только нужные.
- Фаерволы — пришлось настраивать исходящие разрешения для push-протокола.
- Задержки между сбором и отображением — настроили частоту сборки (15s) и агрегацию.
- Добавили метаданные (теги окружения, роли) через relabel_config в vmagent.

6. **Как вы организовали централизованный сбор логов с Loki для гибридной инфраструктуры (Windows + Linux)? Какие challenges были при интеграции Windows Event Log?**

Мы используем Promtail для Linux (собирает логи из syslog, journald, и файлов приложений) и Windows Event Forwarder (или собственный агент на основе python + win32evtlog) для Windows. Для унификации мы выбрали Grafana Agent в режиме logs, который умеет работать и на Windows, и на Linux.
- На Windows мы настроили сбор Event Log (Application, System, Security) и файлов логов (IIS, Exchange).
- Логи обогащаются лейблами: host, service, env, severity.
- Для потоковой передачи используем протокол HTTP push в Loki.

Проблемы:
- Большой объём Security-логов — пришлось фильтровать по Event ID и использовать агрегацию на стороне агента.
- Структурирование Windows Event Log (поля не всегда парсятся) — написали парсер на LogQL с regex.
- Синхронизация времени между хостами — настроили NTP везде.
- Быстрый рост индекса — настроили retention и использование чанков в Loki.

7. **Вы внедрили алертинг на основе логов для выявления аномалий, например, ошибок аутентификации и падений сервисов. Как вы реализовали это с Loki и Alertmanager?**

Мы используем Loki в связке с Grafana и Alertmanager. В Loki есть функция создания правил алертинга (аналогично Prometheus) с использованием LogQL.
- Мы написали правила, например: count_over_time({job="windows"} |= "Authentication failure" [5m]) > 10 → отправка в Alertmanager.
- Для падений сервисов: count_over_time({job="postgres"} |~ "FATAL|ERROR" [1m]) > 0.
- Alertmanager обрабатывает эти алерты, группирует, маршрутизирует по каналам (Telegram, email) с эскалацией.
- Также настроили дедупликацию и тишину для регулярных плановых работ.
- Для уменьшения ложных срабатываний добавили for: 2m (алерт срабатывает только после того, как условие выполняется в течение 2 минут).
- Интегрировали с графиками в Grafana для быстрого перехода к логам и метрикам.

8. **Как вы сократили MTTR на 40% с помощью корреляции метрик и логов в одном интерфейсе? Приведите пример реального инцидента.**

Мы объединили метрики (Prometheus/VictoriaMetrics) и логи (Loki) в дашбордах Grafana, используя общие лейблы (например, app, host, env). Когда происходит алерт, в дашборде уже видны и графики метрик, и логи соответствующего сервиса.
Пример: был алерт о высокой задержке ответа Postgres. Раньше мы бы лезли в логи через SSH, затем смотрели метрики в Zabbix. Теперь открываем дашборду Postgres, видим пик latency, затем переходим в панель логов Loki, фильтруем по хосту и времени — видим много deadlock сообщений. Быстро поняли, что проблема в конкурентных транзакциях, переключились на анализ кода. Время диагностики сократилось с 20 минут до 5–7 минут. Также мы добавили correlation: клик по алерту ведёт на готовый дашборд с нужными панелями.

9. **В вашем стеке есть Keycloak. Расскажите, как вы его настраивали для SSO и как интегрировали с Kubernetes и ArgoCD.**

Keycloak развёрнут в Kubernetes как StatefulSet с использованием Helm-чарта (который мы адаптировали). База данных — внешний PostgreSQL (Patroni кластер).
- Для SSO мы создали клиентов для Grafana, ArgoCD, GitLab, а также внутренних микросервисов (OpenID Connect).
- Настроили федерацию с AD (LDAP) для импорта пользователей, синхронизацию групп.
- В ArgoCD включили авторизацию через OIDC, указав Keycloak как провайдер. Настроили RBAC-политики: разные команды имеют доступ только к своим namespace через mapping groups в Keycloak.
- Для Kubernetes использовали kubelogin или oidc-auth для доступа администраторов.
- Также настроили автоматическое обновление клиентских секретов через Vault (храним их как внешние секреты).

Проблемы: настройка CORS для публичных клиентов, время жизни токенов и обновление через refresh token.

10. **Вы разработали библиотеку Helm-чартов для унификации конфигураций всех окружений. Расскажите структуру и как вы обеспечиваете кастомизацию между dev/prod.**

Мы создали базовый чарт (base-chart), который содержит общие шаблоны для deployment, service, ingress, configmap, secrets, а также пробы и жизненные циклы. Каждый микросервис наследует этот чарт через зависимость или через общий values.yaml.
- У нас есть корневой values.yaml для каждого окружения (dev, stage, prod), которые переопределяют параметры: реплики, ресурсы, домены, переменные окружения, настройки БД.
- Для ещё более тонкой настройки мы используем configmaps с шаблонами Jinja2 (до этого Ansible, но теперь всё в Helm).
- Мы также используем библиотеку _helpers.tpl для общих функций (генерация имен, лейблов).
- Для секретов используем SealedSecrets или External Secrets (с Vault) вместо plaintext.
- В GitLab CI мы запускаем helm template и сравниваем diff перед деплоем.

11. **Как вы внедрили GitOps-подход с ArgoCD и синхронизацией состояния кластера с Git-репозиторием? Какие преимущества получили?**

Мы развернули ArgoCD в кластере, настроили App-of-Apps паттерн: один корневой Application, который описывает все остальные микросервисные Application. Репозиторий содержит все Helm-чарты и значения.
- После каждого merge в main ветку (через GitLab CI) мы обновляем Helm-значения (image tag) и коммитим их в репозиторий. ArgoCD автоматически синхронизируется (авто-синк включён) через webhook, который мы настроили в GitLab для уведомления ArgoCD об изменениях.

Преимущества:
- Полная прозрачность — состояние кластера полностью соответствует git-репозиторию.
- Упрощённый откат (git revert).
- Исключены ручные правки через kubectl.
- Улучшенный аудит — все изменения проходят через MR.
- Мультитенантность через RBAC.

12. **Вы упомянули Blue/Green и RollingUpdate стратегии для zero-downtime релизов. Как вы выбираете между ними в зависимости от ситуации?**

- RollingUpdate — используем по умолчанию для большинства сервисов: он постепенно заменяет старые поды новыми, без удвоения ресурсов. Настраиваем maxSurge и maxUnavailable для контроля скорости. Подходит для сервисов с низкими требованиями к тестированию канареечной версии.
- Blue/Green — применяем для критичных сервисов, где требуется полное тестирование новой версии перед переключением трафика. Мы создаём два деплоймента (blue и green), переключаем сервис на green, когда пройдены интеграционные тесты. В Kubernetes мы используем два набора pod с разными лейблами и меняем селектор service.
- В GitLab CI мы автоматизируем переключение через изменение значения image.tag в Helm values и руками (или автоматически) активируем переключение через ArgoCD.

13. **Как вы настраивали автоматическое восстановление для стандартных сценариев через Ansible и Kubernetes? Приведите пример.**

Для Kubernetes мы используем livenessProbe и readinessProbe, которые перезапускают pod при падении. Для более сложных сценариев (например, зависание сервиса, но pod живой) мы используем плагин kube-state-metrics + Prometheus алерты, которые триггерят внешний обработчик (например, webhook в GitLab, который запускает Ansible плейбук).
Пример: если Postgres кластер Patroni теряет лидера и не может переизбраться, алерт отправляется в Ansible AWX, который запускает плейбук для принудительного перезапуска Patroni на всех узлах или вызова patronictl reinitialize.
Также для самовосстановления мы используем cron-задачи на хостах (например, для очистки дисков), которые управляются Ansible.

14. **Вы разработали Runbooks для частых инцидентов. Расскажите процесс создания и поддержки этих Runbooks.**

Мы организовали репозиторий (в GitLab) с разметкой в формате Markdown или AsciiDoc, структурированный по типам инцидентов (сеть, БД, приложение, инфраструктура). Каждый Runbook содержит:
- Симптомы и триггеры (как распознать).
- Пошаговые инструкции с командами (например, kubectl describe pod, systemctl restart).
- Плейбуки Ansible или ссылки на скрипты для автоматического исправления.
- Контактная информация эскалации.

Мы внедрили процесс: после каждого инцидента мы проводим Post-Mortem, и если проблема повторилась, мы добавляем или обновляем Runbook. Также делаем регулярные тренировки (fire drills) для команды. Runbooks интегрированы с системой тикетов (Jira) — при создании инцидента автоматически предлагается ссылка на нужный Runbook.

18. **В вашем опыте есть миграции серверов до актуального ПО. Расскажите о самом сложном обновлении (например, Windows Server 2012 → 2022 или PostgreSQL major upgrade).**

Самое сложное было обновление кластера PostgreSQL с 11 до 14 (через Patroni) в продакшене. Мы использовали стратегию pg_upgrade с минимальным даунтаймом.
- Сначала на staging развернули рядом новый кластер с версией 14 (отдельный патрун-инстанс), прогнали pg_upgrade, измерили время и пересобрали расширения.
- Мы протестировали процедуру в staging, измерили время.
- В продакшене мы переключили трафик на вторичный кластер, выполнили upgrade на мастере, затем переключили обратно.

Проблемы: совместимость расширений (плагины), нужно было пересобрать некоторые, а также индексы потребовали перестройки (REINDEX).
Также обновляли Windows Server: использовали in-place upgrade после полного бэкапа, но в некоторых случаях делали параллельный развёртывание и миграцию ролей (AD, DNS). Для этого использовали Ansible для автоматизации настроек.

19. **Вы работали с Proxmox и VMware. Сравните эти гипервизоры с точки зрения автоматизации и управления.**

- VMware — промышленный стандарт, мощный API (vSphere), глубокие возможности DRS, HA, FT, хорошая интеграция с Ansible и Terraform (через provider). Управление через vCenter, более зрелый, но дорогой.
- Proxmox — open-source, легче, использует KVM и LXC, имеет собственный API, также поддерживается Terraform (через provider). Меньше enterprise-функций, но удобен для небольших инфраструктур.

Для Proxmox использовал Ansible (модуль proxmox_kvm) и Terraform (провайдер telmate/proxmox). Преимущества VMware — более стабильное управление ресурсами, но Proxmox быстрее разворачивается для dev-сред.

26. **Как вы настраиваете мониторинг с использованием SLO (Service Level Indicators) и Alertmanager? Расскажите про процесс выбора SLI.**

Мы определяем SLI для каждого сервиса на основе бизнес-критериев:
- Доступность (availability) — процент успешных запросов (например, http_requests_total{code!~"5.."} / total).
- Задержка (latency) — 95-й перцентиль времени ответа.
- Скорость обработки (error rate).

Для каждого SLI настраиваем SLO (целевое значение, например, 99.9%).
Далее создаём правила записи в Prometheus для агрегации этих метрик по сервисам и окружениям.
Alertmanager используем для уведомлений, когда SLO нарушается в течение окна (например, > 5 минут).
Также внедрили «error budget» — буфер ошибок, который отслеживаем в Grafana для принятия решений о релизах.

Сложности:
- Перенос существующих алертов: пришлось переписать их на Prometheus rules и Alertmanager.

- Интеграция с Windows-хостами (windows_exporter).
- Хранение метрик — выбрали VictoriaMetrics за её эффективность и долгосрочное хранение.

Мы провели поэтапный переход: сначала new stack для новых сервисов, затем переключение старых.

56. **Вы указали, что настраивали Postfix + Dovecot. Расскажите подробно, как вы настраивали DKIM, SPF и DMARC, и как вы отслеживаете их валидность.**

- SPF — добавляем запись TXT в DNS: v=spf1 mx ip4:... include:_spf.example.com ~all.
- DKIM — генерируем ключи (opendkim-genkey), публикуем селектор как TXT запись, в Postfix включаем smtpd_milters и non_smtpd_milters, указываем на opendkim socket.
- DMARC — публикуем _dmarc.example.com с политикой p=quarantine или reject, указываем агрегатные и форензик-отчёты на почту.
- Для мониторинга используем DMARC Report Analyzer (например, сторонний сервис) и настраиваем алерты в Loki на наличие ошибок в логах Postfix (например, DKIM signature failure).
- Также проверяем через MXToolbox и Google Admin Toolbox на предмет правильности записей.

- Veeam — это enterprise-решение с глубокой интеграцией с VMware, Hyper-V, физическими серверами, поддерживает application-aware, синтетические полные бэкапы, репликацию и облачное хранение. Мы использовали его для критичных систем с SLA 15 минут RPO.

58. **Вы настраивали CI/CD пайплайны с кешированием и артефактами. Расскажите, как вы управляете кешем зависимостей (например, npm, pip) в GitLab CI, чтобы ускорить сборку, и какие подводные камни были.**

В GitLab CI я использую cache с ключами, например, для pip — кеширую ~/.cache/pip, для npm — node_modules. Чтобы избежать проблем с устаревшими зависимостями, мы используем cache:policy: pull-push и инвалидацию по хешу package-lock.json или requirements.txt.
Подводные камни:
- Большой размер кеша, который замедляет загрузку/выгрузку артефактов — настраиваем cache:key с динамическим вычислением (например, по хешу файла).
- Иногда возникала проблема, когда кеш повреждался (например, из-за сбоя загрузки) — тогда мы использовали cache:fallback_keys или очистку кеша вручную через API GitLab.
- Для бинарных артефактов (например, собранных jar) мы используем artifacts с expire_in, чтобы не захламлять хранилище.
